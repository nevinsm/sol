# Resolution: Fix ledger telemetry attribution (sol-3e88d749a6b88dd5)

## Root cause

`internal/runtime/helpers.go`'s `BuildTelemetryEnv` builds the
`OTEL_RESOURCE_ATTRIBUTES` env var's `service.name` field from
`RuntimeDescriptor.Name`. For the claude runtime, `Name` is `"claude"`.

The ledger's extractor registry (`internal/ledger.New`) routes incoming OTLP
log records to a runtime's `ExtractTelemetry` implementation by looking up
`l.extractors[serviceName]` — and it has always registered Claude's extractor
under the key `"claude-code"` (added in 531ea90, March 2026, never changed
since). `"claude" != "claude-code"`, so every claude session's telemetry POST
reaches the ledger, gets HTTP 200, and is silently dropped inside
`processResourceLogs` at the "look up extractor" step (`internal/ledger/ledger.go:424-428`)
— exactly the failure mode ADR-0033 warns about ("A mismatch silently drops
telemetry").

**Where the mismatch was introduced:** before the ADR-0041 thin-runtime-contract
port, the old `internal/adapter/claude` code hardcoded the literal string
`service.name=claude-code` directly in its telemetry-env builder. Commit
`0bfa86b` ("Build internal/runtime/ foundation") replaced that per-adapter
hardcode with the generic helper `attrs += ",service.name=" + d.Name`, and the
claude runtime's `Name` field had always been `"claude"` (never `"claude-code"`
— confirmed via full git history of the `Name:` field). This silently
substituted the wrong value the day the generic helper started being used
(`fe2edb4`, same day, deleted the old adapter). Codex was unaffected because
its `Name` (`"codex"`) already happened to match its ledger extractor key.

**Why this wasn't "OTEL vars missing from the env"**: the writ's evidence
(env vars observed missing in a live envoy session, gathered via `env` inside
a Bash-tool call) reflects Claude Code's shell-snapshot mechanism for its Bash
tool, not the actual `claude` process environment. I confirmed directly via
`/proc/<claude-pid>/environ` on my own live outpost session that every
OTEL_* var and CLAUDE_CODE_ENABLE_TELEMETRY were present and correct in the
real process env the whole time — `startup.Launch`'s env-construction code
(`internal/startup/startup.go`, the `BuildTelemetryEnv` call site) was never
broken at the "are the keys present" level. The regression is entirely in the
*value* of `service.name` inside `OTEL_RESOURCE_ATTRIBUTES`, which is invisible
to an env-presence check and only manifests as silent drops downstream at the
ledger. This also matches the ledger's `requests_total` heartbeat counter
sitting at 0 the entire time despite the ledger being up, healthy, and
reachable (that counter only increments on a *successfully written* token_usage
row, not on HTTP requests received — so "0 requests" was consistent with
"receiving POSTs that all get silently routed to nowhere," not "receiving no
POSTs at all").

I confirmed this decisively by sending two identical synthetic OTLP payloads
to the live ledger, differing only in `service.name`: `"claude"` produced
HTTP 200 with zero rows written; `"claude-code"` produced HTTP 200 and a
correctly joined `token_usage` row. (Diagnostic rows deleted after
confirming.)

## Fix

Added `RuntimeDescriptor.TelemetryServiceName` (`internal/runtime/runtime.go`),
deliberately independent of `Name` — `Name` also drives on-disk paths
(`.claude-config/`, `CLAUDE.local.md`, credential file locations) that must
never change, while the OTLP wire-level service identity is a separate
contract that only needs to match the ledger's registry.

- `BuildTelemetryEnv` now uses `d.TelemetryServiceName`, falling back to
  `d.Name` when unset (keeps existing/stub descriptors working unchanged).
- `internal/runtime/claude/claude.go`: `TelemetryServiceName: "claude-code"`.
- `internal/runtime/codex/codex.go`: `TelemetryServiceName: "codex"` — set
  explicitly for CC-9 symmetry even though it already matched `Name` (no
  behavior change for codex; its `Seed()` already independently hardcodes
  `X-Sol-Service = "codex"` in `config.toml`, since codex attributes via
  `X-Sol-*` headers rather than `OTEL_RESOURCE_ATTRIBUTES`).

This is the only code change. Both outpost and envoy paths go through the
same `startup.Launch` → `BuildTelemetryEnv` call site, so both are fixed by
this one change; no per-role wiring existed to diverge in the first place.

## Regression test (task item 4)

`internal/startup/startup_test.go`:
`TestLaunchTelemetryEnvPresentWhenLedgerPortConfigured` and
`TestLaunchTelemetryEnvAbsentWhenLedgerPortZero`, each table-driven over
`role ∈ {outpost, envoy}`, using the real claude runtime through
`startup.Launch` with `SOL_SESSION_COMMAND` isolation
(`setupTestEnv`/`mockSessionStarter`, no real process spawned). They assert:

- OTEL_* + `CLAUDE_CODE_ENABLE_TELEMETRY` keys present when the ledger port
  is configured (default 4318, no `sol.toml` override) and absent when
  `[ledger] port = 0`.
- **Critically**, that `OTEL_RESOURCE_ATTRIBUTES` contains
  `service.name=claude-code`, not `service.name=claude` — key-presence alone
  would have passed throughout this entire regression, since the keys were
  never missing. Confirmed (see Verification #2) that this specific assertion
  is what fails against the pre-fix code.

## Scope notes (per writ instructions, not implemented)

The writ explicitly asked me not to redesign telemetry or add monitoring for
silent-ingest gaps, but to note the idea: this failure mode (ledger receiving
and 200-ing a request that gets silently dropped due to an unrecognized
`service.name`) is invisible to every existing health signal — the ledger
heartbeat reports "running" throughout, and `requests_total` only counts
successful writes, not received-but-unroutable requests. A cheap follow-up
would be for `processResourceLogs` to log (or increment a distinct counter
for) records dropped due to an unknown `service.name`, so a future
registry/descriptor drift like this one surfaces immediately instead of
requiring after-the-fact archaeology across 60054 rows and a two-month gap.
