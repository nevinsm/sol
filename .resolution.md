# Resolution: CLI consistency fixes

Source doc: `sol-8d4afcfa0390dd73` findings.md ("CLI consistency audit"), Confirmed fixes section (10 items).

## Mandatory minimum

1. **`--description-file` on `sol writ create`/`sol writ update`.** New shared
   `internal/cliflag.ResolveText` helper: accepts a path, or `-` for stdin; errors if
   both `--description` and `--description-file` are set. Unit tests cover path,
   stdin, and mutual exclusion.
2. **`sol caravan <sphere-level-subcommand> --world`.** `commission`, `drydock`,
   `reopen`, `close`, `delete`, `list`, `status`, `remove`, `set-phase` now accept
   `--world` instead of erroring with Cobra's bare `unknown flag: --world`. When
   passed, it's validated via `config.ResolveWorld` (same helpful error as
   `add`/`create`/`launch`); when omitted, no resolution is attempted — these
   commands operate on the caravan/item ID alone and never needed a world. This
   goes further than confirmed-fix #4's suggestion (see below).

## Confirmed fixes — implemented

- **#1 envoy delete SOL_WORLD.** `cmd/envoy.go`: swapped `RequireWorld` +
  `MarkFlagRequired("world")` for `config.ResolveWorld`, matching every sibling
  envoy subcommand.
- **#2 forge sweep confirm gate + fail-closed repo resolution.** `--confirm` now
  required to actually delete branches (dry-run preview + exit 1 otherwise, mirrors
  `caravan close`). Added `dispatch.ResolveSourceRepoStrict` / `cmd.openForgeStrict`
  so a world with no managed/configured repo fails closed instead of silently
  sweeping whatever repo the caller's cwd happens to be in. Scoped to `sweep` only
  (per the doc's own "at minimum forge sweep") — other forge subcommands keep the
  legacy cwd-discovery convenience via the original `ResolveSourceRepo`.
- **#3 world sleep --force confirm gate.** Added `--confirm`; without it, `--force`
  now previews which agent sessions/writs would be affected and exits 1 without
  mutating any state, instead of executing the hard-sleep path unconditionally.
  Updated 3 existing integration tests to pass `--confirm` alongside `--force`.
- **#4 caravan --world dead end.** Superseded by the mandatory minimum above:
  implemented full acceptance (register + validate-when-present) rather than the
  doc's cheaper "helpful rejection message" suggestion, per the writ's explicit
  instruction to make these subcommands *accept* `--world` consistently with `add`.
- **#5 writ --kind validation.** `cmd/writ.go`: `--kind` now validated against the
  known set (`code`, `analysis`) before create, matching the `--status`/`--priority`
  validation pattern already in the file.
- **#6 long-text file/stdin alternative.** Shared `internal/cliflag.ResolveText`
  applied to the 5 call sites the doc calls "highest-value... in order": `writ
  create --description`, `writ update --description`, `handoff --summary`, `mail
  send --body`, `escalate`'s positional description (new `--description-file`,
  with a custom `Args` func since the positional becomes optional when the file
  flag is used). **Skipped** the doc's further "plus `--reason`/`--subject`/
  `--message`" extension — the doc itself downgrades these to "lower-risk
  individually" / "low priority" in its own table, and the writ's acceptance
  criteria only calls out `--description-file` specifically; treated as a
  deliberate scope boundary rather than an oversight.
- **#7 escalate zero-args message.** Custom `Args` func replaces
  `cobra.ExactArgs(1)`, giving `usage: sol escalate <description> — describe the
  problem you need help with` instead of Cobra's bare arity error.
- **#8 resolve error double-wrap.** `cmd/resolve.go` no longer wraps
  `dispatch.Resolve`'s errors in `"failed to resolve writ: %w"` — every error
  `dispatch.Resolve` returns is already fully contextualized (e.g. `"failed to get
  agent %q: ..."`), so the outer wrap only added repetition and, for the
  agent-lookup case, a misleading "writ resolution" frame before any writ was ever
  looked up.
- **#9 mail send world resolution.** Added `config.ResolveWorldHint` — same
  flag→SOL_WORLD→cwd precedence as `ResolveWorld`, but *without* existence
  validation. Using `ResolveWorld` directly (as the doc literally suggests) broke
  an existing test (`TestMailSendWorldFlagCanonicalizes`, which passes a `--world`
  hint that doesn't correspond to an initialized world) — `mail send`'s `--world`
  is a canonicalization hint, not an authoritative scope, so existence validation
  is the wrong behavior here even though the missing cwd-fallback was a real gap.

## Confirmed fixes — skipped

- **#10 caravan create world resolution.** The doc's proposed fix ("resolve world
  unconditionally... still allowing empty result to mean 'no items yet'") isn't
  implementable as literally stated — `config.ResolveWorld` has no "allow empty"
  mode, it always errors when nothing resolves. More importantly, the underlying
  premise doesn't hold: a `Caravan` record has no `world` field (only `CaravanItem`
  does), so when `sol caravan create <name>` is called with zero items, the
  `world` variable computed at that point is never used for anything — there is no
  state that "silently propagates" to later `add` calls, each of which
  independently resolves its own `--world`/`SOL_WORLD`/cwd. Implementing the
  literal suggestion (resolve unconditionally) would instead be a regression: it
  would newly require a resolvable world for a legitimately context-free operation
  (creating an empty sphere-level caravan shell with no items). Skipped as
  ambiguous/premise-doesn't-hold rather than implemented as speculative scope
  creep.
